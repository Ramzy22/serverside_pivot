## Performance vs pre-cutover

`scripts/benchmark_pivot_runtime.py` (identical script on both trees; median of 3 runs, 7 repeats each;
rows × region/product, columns = quarter; ms). Pre = M3 gate (`90d2dcc`), post = this gate.

| Rows | | Load | Cold pivot | Repeat p50 | Repeat p95 | 200-row viewport |
|---|---|---|---|---|---|---|
| 100k | pre | 170 | 187 | 70 | 155 | 43 |
| 100k | post | 156 | 266 | 51 | 60 | 96 |
| 1M | pre | 456 | 224 | 78 | 150 | 55 |
| 1M | post | 471 | 272 | 54 | 60 | 88 |

- Repeated reads are faster (p95 −60%): the core result tier (scope-keyed, dropped on load and mutation, TTL).
- Cold reads carry a **fixed** per-request overhead of about 30–50 ms. A profile of the 1M viewport request
  breaks the post-cutover time into 10–17 ms of Ibis expression construction, about 20 ms of SQL generation,
  and about 50–65 ms of DuckDB execution. DuckDB execution is on par with legacy; the SQL is one scan into leaf
  partials, then re-aggregation. The overhead does not grow with data size (+48 ms at 1M against +79 ms at 100k
  for the cold pivot).
- No latency budget was adopted before the cutover (`docs/flagship-performance.md`: "Rerun on the target
  deployment hardware before adopting any budget"). This gate therefore records the deltas and their cause
  rather than a pass against a threshold.

Carried to M5:
- a plan-tier cache of compiled statements, to remove the fixed compile and SQL-generation cost on cold reads.
  It must be keyed by fingerprint, scope and revision, and must exclude plans with in-memory tables.
- budget adoption on target hardware;
- the TS client-mode column order (REQ-PIV-002);
- the Oracle DB cross-backend question;
- typed errors for Oracle first/last/array_agg;
- the flaky xdist tests: browser and wheel-install tests that pass serially.

Spec-only features answered with a typed `unsupported_query` error (never a fallback or a silent partial
result): keyset `cursor`, grouping sets (`grouping_config` rollup/cube), explicit `subtotals`, `drill_paths`,
measure-axis members that are derived measures, OR/nested filter groups that name a measure, and colliding
pivot column keys (REQ-PIV-001).
