## Backend gaps found and how each is handled

Each was a wrong number, a crash or a raw driver error before this milestone.

| Backend | Gap | Resolution |
|---|---|---|
| Polars | `count_distinct` counted NULL as a value | Lowered as `nunique(where=notnull)` on every backend (REQ-AGG-003) |
| SQLite, Polars | The NULL-safe semi join (`LEFT SEMI` / non-equality predicates) is rejected | Portable form: inner join on `(k IS NULL, COALESCE(k, zero))` pairs against distinct keys. DuckDB keeps the native semi join (about 35% faster at 2M rows) |
| SQLite | Tenor sort key overflowed the SQLite parser (37 KB of nested CASE) | Flat `CASE` forms: 5.5 KB, identical results on all three backends |
| Polars | Panic on a NULL-guarded `min`/`max` over constants only inside an aggregation (e.g. `max(min(0, 0), m)`) | Formula subtrees without measure references are folded in Python (exact IEEE operators only; `round` stays with the backend) |
| SQLite | No `median`, `isnan`/`isinf` (so no formulas); ordered aggregates fail to compile | Typed `BackendCapabilityError` (`unsupported_query`) before execution, from `backend.has_operation` over the expression graph and Ibis compile errors |
| Polars | Ordered `first`/`last`/`array_agg` with a filter fails at execution | Known gap: refused before execution |
| SQLite | Sample variance/stddev raise on any one-value group (data dependent) | Known gap: refused before execution for every input |

The router maps `BackendCapabilityError` to the public `unsupported_query` code.

## After the gate (2026-11-24): branch review and plan-tier compile cache

`/code-review high` over `master...feat/golden-core` reported 10 findings. Each was checked against the code;
9 were confirmed and fixed with a test (the important ones shown red on the old code); one did not reproduce.

| Finding | Resolution |
|---|---|
| A read overlapping a load or mutation stored its stale result (result tier, visible counts) | Core cache epoch, bumped under a lock by every core invalidation (local or from another process); a result or count is stored only under the epoch its read began with (async and sync paths) |
| Measure-axis formula members left out of the plan identity | `canonical()` includes the member expression |
| Materialized pages dropped derived measures and pivot cells | `_slice` returns every value column; the property test compares values, not only paths |
| One materialization blocked the Pager for every tree and tenant | Build outside the lock with a per-tree in-flight marker: other trees proceed, the same tree is built once |
| Ragged/axis helper measures leaked into pivoted responses | Hidden measures skipped in cells and row totals |
| REST `/pivot` offered a `next_cursor` the server refused | `next_cursor` is an offset continuation (`{"offset": n}`) the core accepts; walking it equals the unpaged result |
| `GET /pivot/schema/{table}` always returned no columns | Names and types from the catalog (no rows read); unknown table 404 |
| A text `filterCondition` raised a 500 | Typed `unsupported_query` refusal |
| Client mode answered `= NULL`/`> NULL` differently from the server (REQ-NULL-003) | The client declines (exact server fallback); bundle rebuilt |
| Full export limited to the viewport's columns | Not reproduced: every pivot column is exported in grid order; kept as a regression test |
